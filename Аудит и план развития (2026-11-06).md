# Аудит проекта и план развития — Hamster Adventures

Дата: **2026-11-06**. Ревью сделано по локальной папке проекта (`Unity 6000.6.5f1`, URP 2D, Input System) и по документации этого репозитория.

> Ограничение: Unity Editor в сессии запустить не удалось (терминал среды падает с `0xC0000142`), поэтому ощущения от игры и Play Mode не проверялись. Всё ниже — выводы по файлам сцены, скриптов, аниматоров и настроек проекта. Там, где нужна проверка руками, это помечено.

---

## 1. Что реально есть в проекте

**Стек.** Unity `6000.6.5f1`, URP 2D (17.6.0), новый Input System (`activeInputHandler: 1`), 2D Tilemap + Extras, 2D Animation, Aseprite importer, Timeline, Test Framework. Версия свежая — это хорошо.

**Сцена `Assets/Scenes/MainLevel.unity`** (последняя открытая):
- `Main Camera` — ортографическая, size 10, фон тёмно-синий, пост-обработка **выключена**, висит `CameraFollow`.
- `Global Light 2D`.
- 5 объектов `Ground*` — один и тот же спрайт 1×1, растянутый масштабом ~5×5 юнитов, белый цвет, `Sorting Order = 0`, слой `Default`. У части есть `Platform Effector 2D` (One Way, Surface Arc 170°).
- `Hamster` и `HamsterGirl` — Rigidbody2D (Gravity 2.5, Interpolate), BoxCollider2D, SpriteRenderer, Animator, `HamsterMovement`. Слой `Players` (3). Ссылки `partner` друг на друга заданы.
- `FallZone` — триггер 1000×2 на y ≈ −20, `FallZone.cs`.

**Скрипты (3 шт., ~370 строк):** `HamsterMovement.cs` (движение, двойной прыжок, «поводок» к напарнику, триггер атаки), `CameraFollow.cs` (midpoint + зум по расстоянию), `FallZone.cs` (только `Debug.Log`).

**Анимации:** у обоих героев по 5 клипов (Idle / Run / Jump / Fall / FastPunch) и по контроллеру с параметрами `IsMoving`, `IsGrounded`, `IsJumping`, `Attack`.

**Управление:** P1 — A/D/W/F, P2 — H/K/U/L. Клавиши зашиты полями в компонент, читаются напрямую через `Keyboard.current`.

**Чего нет вообще:** врагов, урона и здоровья, UI/HUD, паузы, звука, префабов (папка `Prefabs` пустая), Tilemap-уровня, фона/параллакса, меню, сохранений, тестов, `.gitignore`, самого git для проекта.

**Документация:** README (по сути готовый GDD), план на 15 этапов (этапы 0–4 закрыты, 5 — следующий), дневник до 2026-10-29. Документация заметно сильнее кода — это редкий и полезный перекос.

## 2. Главный вывод

Фундамент для прототипа собран правильно: персонаж, двойной прыжок, анимации, кооп-камера, односторонние платформы, падение в яму. Это ровно тот объём, который обычно ломает новичка, — он пройден.

Дальше проект упрётся не в «ещё одну механику», а в три вещи: **отсутствие версионного контроля проекта**, **архитектура геймплея на Animator-триггерах** (не выдержит комбо, урона и отмены атак) и **порядок работ** (по плану броски и суперы идут раньше первого играбельного уровня).

Реалистичная оценка: вертикальный срез — 6–8 недель при 10–15 ч/нед; полный объём из README (7 уровней, 5 суперов, лагерь, профили, 2P, боссы) — 1,5–3 года. Это нормально, но в план нужно заложить сокращение объёма после среза, а не до него.

## 3. Риски и что с ними делать

### P0 — сделать на этой неделе

**1. У проекта нет системы контроля версий.** В GitHub лежат только 5 `.md` и 4 `.png`. `Assets/`, `ProjectSettings/`, `Packages/` не версионируются, `.gitignore` нет, а рядом лежит `Library` на 34 000 файлов. Любой неудачный рефакторинг сцены откатить нечем.
*Как закрыть (полдня):*
1. Поставить [Git LFS](https://git-lfs.com/) (`git lfs install`).
2. В корне проекта: `git init`, добавить стандартный Unity `.gitignore` (GitHub → шаблон `Unity`) — игнорировать `Library/`, `Temp/`, `Obj/`, `Logs/`, `UserSettings/`, `Build/`, `*.csproj`, `*.sln`, `.vs/`, `.idea/`.
3. В `.gitattributes`: `*.png filter=lfs diff=lfs merge=lfs`, то же для `*.psd`, `*.kra`, `*.wav`, `*.mp3`, `*.ttf`.
4. Первый коммит — только `Assets/`, `Packages/`, `ProjectSettings/`, `.gitignore`, `.gitattributes`. Далее — ветки: `main` + рабочая ветка на задачу, коммит после каждой проверенной вещи.
5. Решить, где живёт проект: отдельный репозиторий `Hamster-Adventures-Game` (проще, чище) или этот же репозиторий с документацией рядом с `Assets/` (удобнее для правды в одном месте). Второй вариант лучше: код и документы меняются одним коммитом.

Почему git, а не Unity Version Control: GitHub у тебя уже есть, LFS-квоты на 8 МБ арта хватит с запасом, а Unity VCS регулярно ругают за производительность и привязку к экосистеме — [обсуждение на форуме Unity](https://discussions.unity.com/t/unity-version-control-why-is-it-terrible/1647889).

**2. Сборка соберёт пустую сцену.** В `ProjectSettings/EditorBuildSettings.asset` единственная сцена — `SampleScene` (шаблонная пустышка с камерой). `MainLevel` в списке нет. Первый же `.exe` будет пустым экраном.
*Как закрыть:* `File → Build Profiles` (в Unity 6) или `File → Build Settings` → перетащить `MainLevel` первой, `SampleScene` убрать/отключить. Проверка — собрать Windows-билд и запустить вне редактора.

### P1 — до начала контента

**3. Атака ничего не делает.** `ReadAttackInput()` вызывает только `animator.SetTrigger("Attack")`. Урона, хитбокса, отбрасывания и прерывания анимации нет. Это честный этап 5, но важно понимать: боевая система — не «добавить скрипт `Enemy`», а слой данных и состояний. Ниже, в плане, расписано, как сделать его так, чтобы потом не переписывать.

Дополнительно: `FastPunch.anim` имеет **`Loop Time = 1`** — анимация удара зациклена. Для атаки это неверно, выключить.

**4. Ввод зашит в персонажа.** `Keyboard.current[leftKey]` внутри `HamsterMovement` — паллиатив. Следствия: геймпад не подключить вообще; переназначение клавиш из меню невозможно в принципе; P2 на H/K/U/L — ручная договорённость, а не схема ввода; при добавлении третьего действия (захват, супер, пауза) каждый скрипт начнёт читать клавиатуру сам. README требует и геймпады, и переназначение для каждого игрока — сейчас это недостижимо.
*Как закрыть (день-два, пока код маленький):* `InputActionAsset` с картой `Gameplay` (`Move`, `Jump`, `LightAttack`, `HeavyAttack`, `Grab`, `Super`, `Pause`), схемы `KeyboardLeft`, `KeyboardRight`, `Gamepad`, компонент `PlayerInput` на каждом герое, ссылки на действия через `InputActionReference`. Переназначение потом делается встроенным `PerformInteractiveRebinding`, геймпады — бесплатно.
Референс: [PlayerInput — документация Input System](https://docs.unity3d.com/Packages/com.unity.inputsystem@7.0/api/UnityEngine.InputSystem.PlayerInput.html).

**5. Камера без границ и «поводок» — понижено до P2 после проверки 2026-11-06.** `CameraFollow` ничем не ограничен: у края уровня покажет пустоту, при падении одного героя в яму уедет за ним вниз. Дистанция между героями ограничена обнулением `linearVelocity` в `FixedUpdate` — задумывалось как «невидимая стена».
*Что показала проверка:* стена не ощущается, и это сходится с расчётом. Порог срабатывания ≈ 22,7 юнита от середины между героями, а полуширина кадра при максимальном зуме ≈ 24,1 — упор приходится за 1,4 юнита до края экрана и читается как мягкий предел, а не как отказ управления. Поэтому `CameraFollow` пока не переписываем.
*Что всё-таки исправить позже:* (а) границы камеры — на краю уровня в кадре будет пустота, а упавший в яму герой утянет камеру вниз за собой; (б) в `ReadJumpInput()` прыжок запрещается, если герой выше напарника больше чем на половину максимального разброса — на вертикальном участке это будет читаться как «кнопка не работает»; проверить отдельно, поставив героев на разные высоты.
*Как закрыть:* границы — `CinemachineConfiner2D` по полигону уровня; слежение за двумя целями — `CinemachineTargetGroup` + `CinemachineFollow` (+ `CinemachinePositionComposer`), это индустриальный стандарт и снимает ручной `SmoothDamp`, зум и джиттер. Известная тонкость с синхронными целями разобрана здесь: [Cinemachine jitter with multiple targets](https://discussions.unity.com/t/cinemachine-jitter-when-multiple-targets-move-in-sync-local-2d-multiplayer/1570552), справка по Target Group — [docs](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.0/manual/CinemachineTargetGroup.html).
Минимум на сегодня, если Cinemachine пока страшно: в `CameraFollow` добавить `minX/maxX/minY/maxY` и `Mathf.Clamp`, а «поводок» и запрет прыжка относительно напарника удалить.

**6. Сортировка нарисованного мира не настроена.** В `TagManager` один sorting layer `Default`, у всех рендереров `Order = 0` — герои, земля и будущие объекты имеют равный приоритет. Пока спрайты не пересекаются, это незаметно; на первом же фоне или кусте герой начнёт пропадать за землёй.
*Как закрыть (10 минут):* `Project Settings → Tags and Layers → Sorting Layers`: `Background`, `Far`, `Mid`, `Ground`, `Characters`, `Props`, `FX`, `UI`. Проставить `Order` у существующих объектов.

### P2 — по ходу контента

**7. Всё живёт в одной сцене, префабов нет.** `Prefabs` пустая, герои и платформы — копии в сцене. Правка коллайдера или скорости — в каждом экземпляре отдельно. Вынести в префабы: `Hamster`, `HamsterGirl`, `Platform_OneWay`, `Platform_Solid`, `FallZone`, позже `Dummy`, `Hyena`.
**8. Уровень — белые квадраты.** Для прототипа нормально, для среза уже нет. Установленные `2D Tilemap` + `Tilemap Extras` (Rule Tiles) дают уровень в разы быстрее и с нормальным краем. Фон — 2–3 слоя параллакса.
**9. `FallZone` только пишет в лог.** Нужен реальный исход (этап 6): герой в состоянии «выбыл», управление выключено, второй продолжает; если живы оба — рестарт сцены.
**10. Мелочи, которые дешево исправить сейчас:**
- `Rigidbody2D → Collision Detection = Discrete`. При `Move Speed = 15` на тонких платформах возможен проскок — поставить `Continuous` обоим героям.
- Дубликат контроллера: `Hamster.controller` не используется сценой (сцена ссылается на `Hamster_Controller.controller`). Удалить, чтобы не путаться.
- У `HamsterGirl` масштаб `z = 3.34` — мусор от копирования; выровнять с `Hamster` (0.5, 0.5, 1).
- Коллайдер героя не совпадает с силуэтом: `size ≈ 3.7×2.7` при масштабе 0.5 → 1.85×1.35 в мире, `offset y = −1.57` → −0.78. Включи Gizmos и проверь, что рамка лежит по телу, а не по пустоте.
- `OnCollisionExit2D` сбрасывает `isGrounded` при выходе из **любого** коллайдера: на стыке двух платформ возможен «мерцающий» прыжок. Считать контакты или проверять `OverlapBox` под ногами.
- `companyName = DefaultCompany` — сохранения лягут в `AppData\LocalLow\DefaultCompany`. Сменить на своё имя до первых сейвов.
- Прыжок без «coyote time» (0,1 с), «jump buffer» (0,1 с) и обрезки высоты при отпускании кнопки. Для ориентира на Silksong это обязательный минимум ощущения — 20 строк кода, ощутимая разница.

## 4. План на 4 недели

Цель месяца — **вертикальный срез, который можно дать другу**: 3–5 минут, старт → платформинг → 2–3 боя → мини-босс → финиш, без ошибок в Console.

### Неделя 0 (полдня) — техгигиена
Git + LFS + `.gitignore`; `MainLevel` в Build Settings; sorting layers; префабы героев и платформ; удалить дубликат контроллера; `Collision Detection = Continuous`; `companyName`.
**Готово, когда:** сборка `.exe` запускается и в ней видна сцена, а `git log` содержит первый коммит проекта.

### Неделя 1 — боевое ядро (этап 5)
- `Health` (текущее/максимальное, событие изменения), интерфейс `IDamageable`.
- `Hitbox` — дочерний объект с `BoxCollider2D (Is Trigger)` на слое `PlayerHitbox`; включается/выключается **Animation Event** на кадрах удара (`EnableHitbox` / `DisableHitbox`).
- `HitData` (ScriptableObject): урон, отбрасывание, hitstop, тип удара. Урон применяется один раз за удар — `HashSet<Collider2D>` на время активного хитбокса.
- Комбо не на Animator-триггерах, а в коде: счётчик + окно ввода 0,4 с + буфер ввода 0,15 с + отмена анимации по `exit time`. Три быстрых → сильный.
- Hitstop 0,05 с и лёгкая тряска камеры — это 80 % «сочности» боя.
- Манекены: `Rigidbody2D (Static)` + `Health`, без ИИ.
**Готово, когда:** удар наносит ровно один урон за замах, комбо из 3 ударов считается, сильный идёт третьим, манекен реагирует и умирает.

### Неделя 2 — враг и последствия урона (этап 6, без броска)
- Одна гиена: конечный автомат `Patrol → Chase → Attack → Stagger → Dead`, дистанции и тайминги в инспекторе.
- Урон игроку, i-frames 0,5 с, отбрасывание.
- Потеря сознания и подъём напарника удержанием; падение в яму = выбывание (без воскрешения).
**Готово, когда:** гиена замечает, догоняет, бьёт; герой теряет HP, падает, напарник поднимает; упавший в яму не возвращается.

### Неделя 3 — камера, HUD, пауза (этап 9, раньше срока)
- Cinemachine: Target Group на двух героев + Confiner по уровню; исключение выбывшего героя из целей.
- HUD: две полоски HP, индикатор суперудара, подсказки кнопок.
- Общая пауза (`Time.timeScale`), меню паузы с настройками игроков.
**Готово, когда:** HUD показывает реальные значения, пауза останавливает обоих, камера не выезжает за уровень.

### Неделя 4 — вертикальный срез (этап 8)
- Tilemap-уровень на 3–5 минут: безопасная зона с манекенами, платформинг, **2–3 арены с блокировкой камеры** и волнами гиен, мини-босс (заглушка с двумя фазами), финишный триггер.
- Фон: 2 слоя параллакса.
**Готово, когда:** друг проходит уровень от старта до финиша, Console чистая, известные баги записаны в дневник.

### Что сдвинуть в большом плане
1. **Этап 7 (бросок напарника и суперы) — после среза, не до него.** Бросок требует 6+ новых анимаций на каждого героя, супер — ещё и эффектов; пока нет врагов и арены, проверить их ценность нельзя.
2. **Этап 9 (HUD/пауза) — внутрь среза.** Без полоски HP бой нечитаем, без паузы его неудобно тестировать вдвоём.
3. **Этап 10 (лагерь) и 11 (профили) — заморозить до среза.** Это самые «дорогие» системы с нулевой отдачей на этапе проверки идеи.
4. **Этап 13 — сократить.** 7 уровней и 5 суперов до среза не планировать; после среза решить, сколько уровней реально делает команда из двух человек за месяц.

## 5. Дизайн-вопросы к первому плейтесту

Это не правки README, а вопросы, на которые ответит только игра вдвоём:

1. **Падение = окончательная гибель на уровне.** Второй игрок доигрывает уровень один, первый смотрит. В beat'em up это частая причина бросить игру. Альтернативы: респавн на чекпоинте со штрафом (потеря части HP/супер-заряда) или «поймать напарника в воздухе». Проверить на срезе и решить.
2. **Общая камера + жёсткий поводок.** В Castle Crashers пространство ограничено ареной, поэтому конфликта за экран нет. У тебя линейный уровень с платформингом: один побежал вперёд — второй упёрся в невидимую стену. Решение жанра — **арены с блокировкой камеры** между платформенными участками (заложено в неделю 4). Это ключевое изменение структуры уровня, его стоит принять до рисования семи уровней.
3. **Нет чисел.** В GDD нет ни HP, ни урона, ни длительности комбо-окна, ни скорости врагов. До недели 1 нужно завести `Balance.md` с таблицей и менять значения только там — иначе баланс будет размазан по инспекторам сцен.
4. **Читаемость боя на двоих.** Два героя, гиены, эффекты и вспышки на одном экране — главный риск «каши». Правила: враг перед атакой делает замах ≥ 0,4 с, эффекты не перекрывают тело врага, у игрока i-frames заметны миганием.

**Про запуск Unity из командной строки.** Редактор стоит здесь: `C:\Program Files\Unity\Hub\Editor\6000.6.5f1\Editor\Unity.exe`. Команды ниже — для **PowerShell**. Символ `^` в конце строки — это продолжение строки для `cmd`, PowerShell его не понимает; здесь используется обратный апостроф, но надёжнее переменные.

Проверка компиляции и импорта без открытия окна (проект должен быть закрыт в редакторе):

```powershell
$unity = "C:\Program Files\Unity\Hub\Editor\6000.6.5f1\Editor\Unity.exe"
$proj  = "D:\dev\Hamster-Adventures\Hamster Adventures"
$log   = "D:\dev\Hamster-Adventures\compile-check.log"

$p = Start-Process -FilePath $unity -Wait -PassThru -ArgumentList @(
  '-batchmode','-quit','-nographics', '-projectPath', $proj, '-logFile', $log
)
"exit: $($p.ExitCode)"
Select-String -Path $log -Pattern "error CS","Scripts have compiler errors"
```

Почему `Start-Process -Wait`, а не просто `& $unity`: `Unity.exe` — оконное приложение, и PowerShell, запуская GUI-программу, **не ждёт** её завершения, а сразу возвращает управление. В итоге `$LASTEXITCODE` пустой, а лог ещё не создан. `Start-Process -Wait -PassThru` ждёт и отдаёт реальный код возврата.

`exit: 0`, в логе есть строка `Exiting batchmode successfully now!` и пустой вывод `Select-String` — скрипты компилируются (проверено 2026-11-06: проект собирается без ошибок). Если Unity открыт, batchmode завершится ошибкой: второй экземпляр не откроет занятый проект (`Multiple Unity instances cannot open the same project`). Сначала закрой редактор.

Сборка Windows (после того как `MainLevel` попадёт в Build Settings):

```powershell
$p = Start-Process -FilePath $unity -Wait -PassThru -ArgumentList @(
  '-batchmode','-quit', '-projectPath', $proj,
  '-buildWindows64Player', 'D:\Build\HamsterAdventures\HamsterAdventures.exe',
  '-logFile', 'D:\dev\Hamster-Adventures\build.log'
)
"exit: $($p.ExitCode)"
```

Проверить, открыт ли Unity: `Get-Process Unity -ErrorAction SilentlyContinue`.

## 9. Как теперь устроен репозиторий

**Сделано 2026-11-06.** Unity-проект и документация живут в одном репозитории `AlekseyHorjakov/Hamster-Adventures`. Папка проекта — она же рабочая копия git; отдельный клон не нужен.

В git попадает: `Assets/`, `Packages/`, `ProjectSettings/`, `.vscode/`, документы и концепты в корне. Не попадает: `Library/` (1,5 ГБ, 34 тыс. файлов), `Temp/`, `Logs/`, `UserSettings/`, `Obj/`, `Build*/`, а также `*.csproj` и `*.slnx` — они генерируются Unity и IDE.

Порядок работы:

```powershell
git pull                     # перед началом работы
git add -A
git commit -m "Что и зачем изменено"
git push
```

- Коммит — после каждой проверенной в Play Mode правки: это точка отката.
- `core.autocrlf` отключён локально: Unity-YAML и `.meta` хранятся в LF и не переписываются при checkout.
- Исходники графики и аудио (`.psd`, `.kra`, `.wav`, `.mp3`) уходят в Git LFS автоматически, PNG — обычными файлами: на бесплатном GitHub LFS-квота 1 ГБ, а спрайты пока занимают 28 МБ.
- Аутентификация git работает через сохранённый в Windows Credential Manager доступ `git:https://github.com`, повторно вводить токен не нужно.
- Резервная копия проекта до перевода на git: `D:\dev\Hamster-Adventures\_backup-pre-git.zip` (24 МБ). Можно удалить — история уже в репозитории.
